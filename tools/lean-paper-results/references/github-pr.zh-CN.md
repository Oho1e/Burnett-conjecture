# 并行交付与 GitHub 合并

本参考属于技能与工程工作流第1.3版；数学标准仍为 `paper-results` 第1.2版。按项目实际采用其中安排，本地交付不因此增加建库义务。

## 项目授权与平台设置

沿用当前项目已经确定的仓库、可见性和操作授权。公开某篇文章的授权不适用于其他文章；技能本身不授权公开、推送或合并。已获明确授权时直接执行相应工作，无需为同一操作重复询问。改变可见性前核对将公开的跟踪文件与历史是否符合项目已确定的分发范围；发现超出授权的内容或凭据时，说明具体问题并先处理该项，其余独立工作继续。

项目采用受保护主线时，建议要求PR、指定必需CI、合并前基于最新主线检查，禁止强推与删除，并使规则覆盖管理员。使用现有等效ruleset即可，不重复叠加保护。记录实际启用的规则和必需检查名称；API失败或套餐限制时如实保留“平台未强制”，不绕过限制或擅自公开/升级。公开仓库在GitHub Free支持分支保护，私有仓库支持范围取决于套餐，配置时核对当前条件。[GitHub分支保护说明](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

## 分支与并行写入

按可独立使用的数学交付建短期功能分支，可以包含必要定义、数条引理及说明；不按代理人数、单条引理或文章切片数量机械建分支。公共定义确有多个消费者时先稳定最小接口；后续任务可以读取冻结版本并行，不必等待全部前置PR合并才开始。

每项任务明确原文范围、输入版本、消费者、可写文件和交付证据。共享目录中不可由多个代理同时切换Git分支；采用隔离worktree，或由协调者维护分支、代理按文件归属提交工件。公共定义、依赖锁、中央清单和公共构建输出由协调者整合；独占目录中的局部检查可以并行。依赖或接口变化时通知受影响任务，仅刷新相关部分。共同闭合组继续共享所需参数、见证和极限次序。

## 草稿 PR 与随交付登记

有可审阅成果即可开草稿PR。说明实际交付、原文位置与Lean声明、未闭合条件、依赖PR和检查/复核入口；可沿用 [PR模板](../assets/repo-template/.github/pull_request_template.md)。不要求先完成整片或整篇才提交审阅。

协调者在同一个合并候选中补齐该交付的代码、库入口、应审计目标登记及准确的范围/说明更新。中央文件可由单人写入，但不能先合代码、再等总整理PR，导致绿色检查漏掉本次新增目标。辅助声明是否单列目标仍按原数学范围与实际依赖闭包判断，不把每条辅助引理都变成独立论文结果。

纯文档、工程配置等PR按实际影响审阅，不强制进行无关的数学反向核验；若其改动影响检查能力、范围或数学说明，应检查相应影响。不要把删除目标、放宽信任或跳过检查混入无关工程修补。

## 独立回读与组合检查

数学成果冻结后，未参与该项正向构造的代理从实际类型及重要定义反向核验，再比较原文；此时其他就绪任务继续。使用已有证据时按 [双向工作流](workflow.zh-CN.md) 核对其适用性。实际陈述、定义、实例或数学解释变化时重查受影响结果；纯证明实现变化经核实不改变含义时可沿用语义判断并更新机器证据，不触发全文重审。

合并前核对最新主线上的组合结果，而不只看功能分支单独绿色。GitHub的 `pull_request` 工作流在默认checkout下检查合并候选；核实本项目没有改成仅checkout head。主线推进后刷新组合候选及相关检查；旧CI继续证明旧快照，不能冒充新候选证据。[PR事件与合并候选](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request)

检查范围匹配交付：实际构建、目标与公理审计、原文/范围结构等沿用项目入口。检查配置或目标清单本身发生变化时，审阅变化是否仍覆盖该交付，不能只凭PR绿色接受检查能力被削弱。普通源码PR使用只读权限CI，不把有写入凭据的待审代码执行当作默认方案。

## 单一合并窗口

协调者核对本次范围、未解决异议、适用复核、目标登记和最新组合CI后，按项目授权合并；子代理提交工件与复核，不各自抢合主线。仅将最终合并窗口串行化，开发、局部检查和独立复核可继续并行。存在真实依赖时按依赖合并，独立PR不因文章顺序额外排队。

短期分支默认建议 `Squash and merge`，使一个可消费交付成为一个主线提交；有保留逐提交历史等实际需求时可选项目已有方式。Squash后不继续在旧分支累积新任务；依赖PR需要更新到实际新主线并保留自身增量，避免带入已压缩的旧提交。核实最终diff后重跑受影响检查，不为整理历史强推主线。[合并方式及短期分支适用性](https://docs.github.com/en/pull-requests/reference/pull-request-merges)

## 合并后证据与状态

确认最终主线提交的push CI真实通过，再报告本次整合完成。失败则暂停后续合并，先定位、修复或在授权范围内回退；不擅自禁用必需检查或删除失败目标。其他独立实现和诊断可继续。只记录实际运行，不将尚在排队的CI写成通过。

保留PR head、所测base/合并候选、原文和关键源码/配置/依赖版本及复核适用范围；Squash产生新SHA时记录PR到最终主线提交的关系，补最终CI链接。已有哈希与CI记录足以定位时无需另建账本，可在PR说明或现有复核记录中补充。仓内记录不填写包含其自身的新提交号，避免为了证据链接不断制造待验证提交。

开发主线可以保留准确标识的条件接口或待作者确认状态，合并不表示该数学义务已闭合。将普通数学解释交用户/作者确认的要求，以及信任政策和整篇覆盖条件，继续按原标准执行；不把每次例行代码合并都升级为新的人工数学批准。原文歧义、补假设或改变结论仍须用户决定，不能先以改后命题宣称完成。

## 账号审批与独立性的区别

独立代理复核是数学审查证据，GitHub的Approve是平台账号审批，两者分别记录。多个代理共用同一账号时不能写成另一账号批准；GitHub不允许PR作者批准自己的PR。单账号项目可要求PR和CI并保留独立复核报告，不设置无法满足的第二账号批准门槛；多人项目按实际审阅者与约定设置批准数，不自动覆盖已有要求。[GitHub审批说明](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/approving-a-pull-request-with-required-reviews)
