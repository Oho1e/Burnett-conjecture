# Lean 论文形式化·结果全覆盖

[English reading copy](SKILL.en.md)

本技能与工程工作流为第 1.3.1 版，沿用数学标准 `paper-results` 第 1.2 版，其范围、信任与完成条件不变。先读 [标准定义](references/standard.zh-CN.md)，再按本轮任务读 [双向工作流](references/workflow.zh-CN.md)。不要继承别的技能中“全文每处数学文字均须覆盖”的要求，也不能把本标准缩成只检查一个主定理。

## 执行入口

- 启动、续接或调整证明：核对当前任务的原文版本、范围和进度；本轮需要沿用完成或复核结论时，核实相应证据是否适用于当前输入。发现变更后按双向工作流判断影响，再确定本轮工作。
- 建立或接入 GitHub 论文工程：按双向工作流核对本轮仓库目标及已有授权，读 [工程接入](references/engineering.zh-CN.md)，按需合并 `assets/repo-template/` 及 `scripts/check_paper.py`；沿用已有等效配置。
- 并行实现或经 PR 整合成果：读 [并行交付与 GitHub 合并](references/github-pr.zh-CN.md)。按数学交付组织分支；新增目标的代码、导入、登记与状态随同一候选整合，独立复核及最终组合检查适用于实际合并版本。仓库可见性、保护设置及最终合并执行者沿用项目选择与已有授权；人类合并模式下交付就绪PR，不代为合并。
- 讨论信任或准备完成说明：读 [信任政策](references/trust.zh-CN.md)，以当前项目已确认的指令和记录为准。未选择时保留待决，不把附带检查器配置当作批准；其他项目或旧会话的待决状态也不能覆盖本项目明确决定。
- 需要解释标准的投稿依据时：读 [来源记录](references/sources.zh-CN.md)，区分期刊明文要求、社区实例和本标准的建议。

## 工作界线

1. 锁定文章版本和文件哈希，建立全部正式结果清单，包括正文及附录的 theorem、proposition、lemma、corollary，以及作为独立结果陈述的关键未编号断言。编号与否不是排除困难命题的理由。
2. 将证明这些结果所需的定义、技术事实和引用定理纳入实际依赖闭包。已有形式库中的合适证明直接复用；并非要重写参考文献全文。
3. 与目标无关的历史叙述、背景旁述、说明性例子或可选证明不自动成为认证目标。若它本身是正式数学结果、被用于证明或被明确宣称已验证，则纳入。边界有实质歧义时逐项交用户决定。
4. 正向从原文构造 Lean 声明与证明；反向从实际类型及重要定义独立读出数学命题，检查对象、假设、量词、常数依赖和全部结论。不得仅核对声明名字或作者写的摘要。
5. 未证数学可暂作显式 theorem 参数或结构字段，准确记为条件接口。最终闭合时从原文条件消除额外前提；不能把结论、全局解或关键估计藏进参数后宣称原定理已证。
6. 允许替代证明，保留原命题及必要假设。若用户另要求核验原文特定证明路线，将其作为额外任务，不能只凭目标已有另一条形式证明就标路线完成。
7. 普通证明代码可以专用于该文章，无须先达到 mathlib 上游的泛化、命名、API 和全套 lint 标准。仍须有可复现构建、准确语义及约定信任下的闭合证据。

## 用户决定与协作

项目采用双语交付时，在同一 PR 中同步更新受影响的中英文说明。代码、目标清单和原始证据各保留一份；以实际声明、锁定原文和同一验证回执核对两种语言的数学覆盖范围、假设与状态。每种工作规范各保留一个正式执行入口。

交付位置与本轮任务一致；单独提供技能或模板不增加安装、建库或发布权限。本轮已有明确的远程操作指令时沿用其授权；目标尚未确定时先推进独立的本地工作。原文含糊条件或必须补加的数学条件，逐项说明选项和影响，等用户决定后再锁定该处建模。用户已经明确的决定不重复询问，其余独立工作继续推进。

推进时按依赖分工，耦合估计及 bootstrap 保留共同闭合责任。输入已就绪、能独立交付且可避免共享写入冲突时，优先用可用子代理并行推进；协调者负责必要共享定义和最终整合，成果可滚动交未参与该项构造的代理反向核验，其余就绪工作继续。并行度随依赖与整合成本调整，不设固定代理配额。

准备完成说明时，由独立代理从实际类型和重要定义形成数学解释，再与原文和正向说明比较；可按需查阅原文符号及约定。另从锁定论文独立核对正式结果范围，再与现有清单双向比对；已有范围复核可按工作流核实适用性后复用。经核对，数学解释仍对应当前实际类型及所需定义、且原确认覆盖本次使用范围时，可沿用已有作者确认；只将数学含义新增、实质变化或范围扩展的部分交用户或作者确认，记录实际确认者、范围和可识别的解释版本。单代理自审可以推进草稿，不能冒称完成独立复核或人类确认。

开发主线可保留明确标识的未闭合接口和待作者确认状态；合并不提升论文认证状态。例行整合沿用已确定的项目操作授权，原文歧义、补条件或改变结论仍由用户决定。子代理复核与 GitHub 账号审批分别记录，同账号操作不冒充另一账号的批准。

完成声明只覆盖本标准定义的正式结果及其必要依赖。机器脚本只报告 `machine-check-passed`，不签发认证。信任决定、全部结果覆盖、语义对应、检查与版本证据缺一项时，如实保留未完成状态。

每次汇报分别说明数学结果、未证接口、机器检查、语义复核与发布状态。面对不熟悉 Lean 的作者，用普通数学语言说明关键差异，不要求其阅读全部证明代码才允许作数学决定。
