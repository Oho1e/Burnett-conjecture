# 多代理并行推进：本工程的规则与试运行

用户希望通过同时启动多个子代理缩短总工期。本轮采用“主代理整合与共享构建、两项独立证明实现、空闲槽滚动复核”的试运行。并行度依据就绪任务和实际工具容量调整；当前环境最多四个活跃代理，包含主代理，这个数量不写成通用skill规则。

## 当前试运行

| 任务 | 数学交付 | 独占写入 |
| --- | --- | --- |
| 完整B展开 | 原文447–448行的实对称分量恒等式及真实Lean证明 | `Burnett/Algebra/QuadraticExpansion.lean` |
| 零锥核与规范交叉 | 非零ξ、s=0时的Ricci核等价关系，以及实双线性F的规范交叉消去 | `Burnett/Algebra/NullKernel.lean` |
| 主代理 | 共用定义、版本与构建协调，最终接口拼接、中央清单、CI及报告 | 共用定义与中央工程记录 |
| 滚动复核 | 从冻结实际类型和重要定义独立回读，再比较原文 | 复核自有证据目录 |

两项实现共用 `RicciSymbol.lean` 与 `QuadraticDefs.lean`。后者只增加对称性、有序四重收缩、张量平方及实双线性物理形式的定义；复Hermitian扩展与零锥商正性仍属于后续义务。零锥核分支不把另一分支的B展开或尚未完成的Hermitian扩展作为前提。

共享定义由主代理先实际构建一次，再记录源码哈希与固定SDK导入环境。实现代理直接读取该版本，使用不同源文件和自有输出目录做Lean检查；公共 `.lake` 构建输出及依赖变更由主代理协调。共享版本若需要改变，先通知受影响任务，再根据实际差异刷新相关证明与检查。只统一本轮需要的定义，辅助引理保留各分支自行组织的空间。

## 现行并行安排

1. 从现有切片及实际进度选择输入已可用的任务；同时考虑它会解除哪些后续阻塞。定义边、证明边和应用边分别解释，避免按文章顺序增加等待。
2. 能独立交付、且可分开写入的任务优先并行。任务包沿用原文、接口及消费者，只补本轮目标、写入责任和交付证据位置。
3. 共享数学定义及中央记录由协调者统一整合；分支提交实际新声明、检查结果和仍缺输入，不自行提升父项状态。
4. 只对会争抢同一输出或变更同一依赖的构建进行串行协调。独占目录中、读取冻结公共依赖的检查可以并行；隔离环境是否值得使用取决于其准备与合并成本。
5. 一个结果达到可检查状态即可交未参与该项正向构造的代理独立回读，同时其他实现继续。已有复核按输入适用性复用；重要定义变化后补查受影响部分。
6. 分支完成、等待输入或发现接口不匹配时重新选择就绪任务。共同估计仍由共同闭合任务核对同一参数、见证和全部结论。
7. 在相应交付范围整合后，由协调者执行合并版本的完整检查、实际目标及公理审计、中央范围更新和本工程已授权的远程CI；多份局部通过不能代替合并检查。

合并与复核使用已保存、可按哈希定位的源码快照，并记录所用公共依赖版本；工作文件可继续开发。哈希不符时核对版本，取得匹配快照或重新建立受影响的检查证据。

代理消息或工具调用失败时，核实已落盘工件及其适用检查记录，再据实际证据续接合并和独立复核；消息状态、机器检查和数学状态分别记录。

## Skill入口的并行原则

1.3版skill已承接以下原则，详细PR整合安排见[GitHub工作流](github-workflow.md)：

> 存在输入接口已就绪、可独立交付且能避免共享写入冲突的任务时，优先使用可用子代理并行推进。由主代理统一必要共享定义与合并责任；并行度随任务依赖、实际等待和整合成本调整。实现成果达到可检查状态后，可滚动交由未参与构造的代理独立反向核验，其余就绪工作继续。

详细分工、共享写入与PR安排位于1.3版workflow参考文档，入口只保留决策规则。1.2版数学标准、旧版归档技能包及个人skills目录均保持不变。

## 怎样判断实际收益

本轮记录实际交付、共享定义准备、依赖等待、检查/合并和返工。主要看经机器检查且语义对应的数学成果何时可被共同闭合点消费。没有可比串行基线时，不报告加速倍数，也不以代理数、文件数或定理条数估计整篇完成比例。

F06是多条后续依赖共同使用的瓶颈候选；现有图没有可靠工时估计，不能仅凭出边数量认定全局关键路径。若共享定义反复变化或分支频繁互等，应调整切口或减少当时的并行度；若阻点转移到F05或外部分析接口，后续调度随之改变。

本次试运行中，一次工作文件在发布哈希后继续修改，复制校验发现不符，随后改用已保存的冻结v1。另一分支在源码与实际编译完成后末次回复发生工具错误，主代理保留实际工件和检查证据，并交独立复核。两者均按实际版本续接，没有将消息状态当作数学状态。
