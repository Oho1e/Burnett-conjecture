# v1.3 skill 独立模拟行为测试

测试日期：2026-11-15。测试对象为 `lean-paper-results/SKILL.md` 及下列按需引用文件；工程工作流为 1.3，数学标准仍为 `paper-results` 1.2。

本报告是七项模拟决策，不是对真实文章、PR 或 CI 的核验。只读取技能文件并写本报告；没有访问网络、操作真实 Git/仓库、运行 Lean、改变信任政策或替真实作者确认。文中的“可合并”指工程条件满足后按既有项目授权整合；“可认证”指能否作出本标准的整篇 `verified` 完成说明，不是官方认证。

关键原文包括：P L45“开发主线可以保留准确标识的条件接口或待作者确认状态”；P L21“不能先合代码、再等总整理PR”；P L31“不能只凭PR绿色接受检查能力被削弱”；W L77 允许核实后的纯证明变更继承语义结论和作者确认；P L49 区分独立代理复核与 GitHub Approve。以下判断以这些操作性规则为依据，不把某个公开示例当成另一项目的授权。

## A：已授权公开与合并；两条支持引理已核验；作者及信任 pending

**实际下一步。** 协调者核对这两条引理的交付范围、库入口/必要登记、现有独立核验的输入绑定，以及题设成功 CI 是否确实对应最新主线上的实际合并候选；把“作者确认待决、信任政策待决”准确保留在记录中。上述例行核对成立，且没有实际未解决的数学异议，就执行已经授权的合并，随后观察最终主线提交的 push CI，再报告整合完成。可以按一个可消费的数学交付组织两条引理，不必机械地每条引理一 PR，也不必等整篇完成。

**合并与认证。** 可以开发合并；不能只因两项 pending 卡住例行合并，也无需重复索要公开/合并许可。不能宣称整篇 `verified`：题设没有给出全部结果覆盖，而且信任决定与作者确认尚缺。CI 候选成功只记录其实际机器检查范围。pending 本身不等于新增未证数学前提，不能因此自动把所有数学结果标为 `conditional`；应分别报告当前证明、未证接口、机器、语义、确认和发布状态。

**谁决定。** 已授权的工程整合由协调者执行；本项目最终信任选择由用户决定，普通数学解释由用户或作者实际确认。若 pending 实际掩盖原文歧义、补假设或改变结论，该处须先由用户决定，不能按“普通 pending”绕过。

**复核范围。** 两条引理、其必要定义/依赖与受影响消费者；核验登记及当前组合，不因局部合并强制重做整篇语义审计。整篇完成说明仍须独立范围核对、全部结果闭合和其余完成证据。

**引用。** S L30、L34–38；R L35–41；T L3、L20–22；P L13、L21、L35–45。

## B：项目乙仅获本地形式化授权，技能带有项目甲的公开示例

**实际下一步。** 继续乙的本地原文锁定、结果清点、证明、独立核验和本地复现；沿用乙已有规则及实际信任决定。不要创建远程库、推送、公开或更改可见性，也不要把甲的 owner/name、公开许可或待决状态复制成乙的项目决定。示例可供工程组织参考。

**合并与认证。** 无权执行远程 PR 合并。本地工作和已有本地整合可按乙授权继续。没有远程授权本身不阻碍将来作出准确的本地完成说明；但题设没有乙的闭合、覆盖、确认等证据，目前不能认证。若将来需要远程发布，先准备具体可审阅的文件及范围，再补相应授权；当前本地工作无需等待这项未提出的需求。

**谁决定。** 用户决定乙的远程目标、可见性和分发范围；协调者执行已经授权的本地工作。乙若已有明确信任政策则直接沿用，不因技能末尾的历史状态重新置为 pending。

**复核范围。** 乙自己的锁定文章、清单、实现和本地固定环境；甲的示例不充当乙的数学或授权证据。

**引用。** S L13–15、L30；W L23–31、L84；P L3、L7；E L7、L29–31、L73；T L3。

## C：审完后 main 改了共用测度定义；PR head 未变；旧 CI 绿色

**实际下一步。** 保留旧审查和旧 CI 为旧快照事实；刷新以最新 main 为 base 的组合候选，并检查测度定义差异。识别它影响的实际类型、定义展开、实例、隐式参数、记号/约定和消费者，对受影响部分重做相应独立语义核验与机器检查。若暂不能判断影响，记录具体疑点并先补查，独立工作继续。

**合并与认证。** 不能凭 head 不变和旧绿色合并，也不能用旧证据对新组合认证。最新组合通过适用检查、异议解决后可按原授权合并，仍须确认最终主线 CI。仅因证据适用性待重核，不自动把原数学状态改成 `conditional`。

**谁决定。** 协调者组织更新与影响定位，独立核验者核查受影响数学含义。若确认其数学含义新增或实质改变，只把相关变化交用户/作者确认；若经核对解释仍相同且旧确认覆盖该范围，可以继承确认，不重复询问整篇。

**复核范围。** 共用测度定义及受影响结果和相关接口；影响可能超过文字签名或公理图显示的直接依赖，但不自动全文重审。更新候选的 base/head、关键定义及机器/语义证据绑定。

**引用。** W L70、L74–80；P L27–29、L35、L41–43。

## D：新增 theorem 未进入库入口及题设所称 scope.targets；其余九目标绿色

**实际下一步。** 先用原文角色和实际依赖确定新 theorem 是独立论文结果、必要辅助声明，还是明确无关的探索内容。若是本次新增正式结果，在同一个合并候选内补齐代码、有效导入/构建入口、准确目标登记及范围说明，再运行覆盖它的真实构建、目标与传递公理检查，并作独立反向核验。不能先合代码，把登记留给以后总整理。

**合并与认证。** 按新增论文结果这一自然读法，当前候选不能接受，九个目标绿色不足以覆盖第十个。若它确实只是辅助声明，不要求每个辅助 theorem 都单列最终目标；仍须有实际进入已审目标依赖闭包或等效本体/依赖核查的证据。题设没有这些证据，不能推断已经覆盖。任何未覆盖的正式结果都使整篇完成说明不成立，不能通过删目标恢复绿色。

**谁决定。** 协调者负责中央导入、目标与范围的同候选整合，独立核验者检查数学对应。原文角色若有实质歧义，由用户据原文决定；明确正式结果不交代理自行降格。新增数学解释若未在原确认范围内，交用户/作者补确认。

**复核范围。** 新结果及必要依赖、相关消费者、当前清单对原文的承接关系，以及包含九项旧目标和本次交付的组合检查。对未改变的九项语义证据可核实后复用，不机械重审。

**引用。** R L9–20、L41；S L14、L22；P L21、L27、L31；E L54–59、L63、L67；W L62、L80。

## E：所有代理共用 Oho1e，却计划要求一个 GitHub Approve

**实际下一步。** 核对 PR 作者账号及实际项目要求。若 PR 作者也是 Oho1e，多代理不能通过同一账号给自己的 PR 提供所需批准；不伪造另一账号批准，也不把独立核验报告写成 GitHub Approve。若只是尚未采纳的流程设计，采用可满足的 PR、必需 CI 与独立数学复核记录，不新增无法满足的第二账号门槛。

**合并与认证。** 若“必须一个 Approve”已经是明确项目约定或平台现行门槛，在满足或获得相应变更决定前不能绕过合并。若它仅是代理的新建议，修正该建议后按真实现行规则及原合并授权推进。账号门槛未实现不等于数学证明有误；反之，得到 Approve 也不能替代作者确认、独立语义核验、机器或整篇覆盖证据，不能据此认证。

**谁决定。** 协调者可纠正自己尚未采纳的不可行建议；既有明确项目批准要求的改变由用户/有权项目负责人决定，不能自动覆盖。真正的另一账号审阅者才能提供其实际平台批准；独立代理继续提供分别标识的数学复核。

**复核范围。** 账号身份、PR 作者、实际规则/必需检查和复核角色记录；不因此重做无关数学审计。

**引用。** S L36；P L9、L35、L49。这里按技能原文判断，未访问 GitHub 验证平台现况。

## F：只改证明；已核实类型、定义、解释、信任配置不变；原作者确认覆盖目标

**实际下一步。** 记录题设已完成的适用性核对及原作者确认范围/解释版本，更新受影响构建、传递公理审计和实现输入绑定；在最新主线组合候选上获得真实 CI 后按授权合并，再确认最终主线 CI。原独立语义结论与作者确认可以继承，无需重复请作者确认，也不强制全文语义重审。

**合并与认证。** 完成上述增量机器检查及例行合并核对即可合并。纯证明变更不会单独否定已有整篇完成状态；但题设本身也不证明整篇原已 verified。只有旧整篇完成依据仍适用且其他条件齐全，才可更新固定版本后继续作相应完成说明。若本项目信任政策仍是 A 中的 pending，F 的“信任配置未变”不能把它变成“已确认政策”，更不能新增认证资格。

**谁决定。** 协调者/复核者检查实际变更及记录适用性，执行原授权；作者无需再次作同一数学决定。若后续核对发现题设不成立、引入信任扩展或改变数学含义，再只将实际变化交用户/作者决定。

**复核范围。** 此次证明实现、受影响构建与公理审计、相关环境和组合候选；语义核对用于证明“不变且覆盖”的事实，不额外重造全部自然语言解释。

**引用。** S L34；W L74、L77、L80；P L27、L29、L41–43；T L3、L22–24。

## G：同一 PR 把 project-check 的真实 Lean/公理检查改为 echo successful，仍显示绿色

**实际下一步。** 拒绝该候选按现状合并，指出绿色源于检查能力被删除。撤销该削弱，恢复真实构建、目标存在/来源及传递公理审计，或提供经审阅且实际等效的检查。核对实际 workflow、被调用脚本、目标清单和执行条件，确认所显示的 job 真正在实际候选运行这些检查，而非只保留名称与状态。

**合并与认证。** 不能合并当前放水候选，也不能称它 `machine-check-passed` 或据其认证。保留 job 名、GitHub Actions 来源与绿色只描述状态上下文，不能证明 Lean 或公理审计发生。该变更影响检查能力，不能以“工程配置 PR 无须数学反向核验”为由跳过对应审查。已授权合并不授权把必要检查掏空。

**应补证据。** 至少包括：可审阅的恢复/等效检查差异；固定工具链、依赖、原文/清单与实际代码版本；最新 main/base、PR head、实际组合候选；实际执行构建和精确目标审计的完整命令/退出状态及对应日志、类型/公理输出和生成结果；覆盖本次交付而未缩减目标的依据；可定位的真实 CI 运行及工件。不能拿旧版本工件或 echo 输出填充这些字段。检查能力本身改变时，应有针对性的有效性验证；例如在隔离维护测试中证明预期坏目标或不允许公理会在预期阶段失败并给出相应诊断，而非任何失败都算审计有效。本次模拟不执行此类测试。修复候选检查通过后，仍须按流程确认最终主线 CI。

**谁决定。** 协调者与工程复核者修复并核对检查能力；无需向作者重复索取未改变的数学解释确认。若有人确实希望降低本项目检查/信任或完成标准，应把具体变化交用户决定并准确改称交付状态，不能用同名绿色静默实现，也不能继续沿用原完整验证措辞。

**复核范围。** workflow、所调用检查脚本、所有相关条件/跳过路径、精确目标登记与实际候选检查覆盖；若数学输入未变，可以复用适用的语义结论。不能因工程配置变化自动要求全篇数学重审。

**引用。** P L23、L31、L35、L41；E L63–75；W L66–70；R L37、L51；S L38。

## 未由题设消除的真实歧义

1. **A 的“已核验”深度。** 未说明是符合技能的未参与构造者从实际类型/重要定义独立回读，还是仅自审/编译。本报告按前者给出可开发合并路径；真实执行前须查既有证据，缺什么只补什么。单代理自审不能冒称独立复核。题设也未明确是否存在真实未解决异议。
2. **A 的候选新鲜度。** “CI 候选成功”没有列明 base/head、checkout 方式及覆盖，因此实际下一步包括核对这些事实；C 则明确主线已变化，旧成功不能复用为新候选证据。
3. **D 的 theorem 角色及配置字段。** 仅有 `theorem` 语法不足以判定必须单列为论文最终目标；原文角色和依赖闭包才决定。本报告把题设 `scope.targets` 当目标登记的概称，实际按现有等效 schema 的 `targets` 处理，不凭措辞创建另一份清单。库入口不是唯一可能的等效显式构建证据，但题设没有提供替代证据。
4. **E 的计划权威及 PR 作者。** 尚未采纳的代理建议、用户明确项目要求、已启用平台门槛是不同状态；技能明确不能自动覆盖既有要求。若实际 PR 作者并非 Oho1e，同账号能否给该 PR 平台批准的判断也不同，应先核对，不凭空假定已存在另一账号。
5. **F 是独立场景还是 A 的后续。** 未说明其信任政策已经确认，亦未说明原项目整篇已完成。因而无条件可继承的是题设覆盖的语义/作者确认；认证结论必须保留条件。“配置不变”与“政策已获用户确认”不同。
6. **“认证”的用语。** 技能本身不颁发官方认证；本报告只使用其 `verified` 和范围准确的项目成果说明含义，不替真实文章补确认或发标签。

以上主要是模拟输入缺失，需要按真实记录核明；未发现七项情境在所读技能指令中有不可消解的规范冲突。尤其“开发合并可带 pending”与“整篇完成须确认齐全”分别约束工程整合和完成说明，不构成矛盾。
