# GitHub分支、PR与合并

2026-11-15用户选择将本工程公开。本流程用于开发成果进入`main`；数学标准仍是paper-results1.2，skill与工程工作流版本为1.3.1。进入主分支不签发整篇形式化标签，未决信任政策和作者确认保持原状态。

## 本轮交付边界与最终执行者

代理完成修改、适用的独立复核、实际候选CI和证据交接，不执行main合并。按2026-11-17用户更新的[目标规则](GOAL.zh-CN.md)，就绪PR待人工合并时，有不依赖其合入main的后续数学任务就自动推进下一独立分支和PR；仅实际依赖阻塞且无独立任务、需用户裁决或确认阻断时才停止。此续接规则不增加main合并、auto-merge或删分支权限。新任务有明确执行者和授权时沿用该决定。

项目选择人类最终合并时，代理在已有PR中交接目标分支、受审head、最新组合CI、适用复核及未解决项、建议squash方式，保持PR未合并。就绪不写为整合完成，不代替人类点击/调用合并API或开启自动合并。项目明确授权代理执行时，再在该范围内使用核对过的head操作。最终合并操作、数学解释确认和整篇完成条件分别记录。

## 并行工作与PR范围

从当前main按可消费的数学交付建立短期功能分支，例如一组相关的零锥引理；不按代理人数或46个切片机械建分支。不同Git检出任务使用独立worktree；共用检出目录时保持同一分支、明确文件写入责任，由协调者暂存和提交，代理不各自切换分支。

实际共享的定义先统一最小接口，消费者可基于冻结版本并行实现。只在确有依赖时使用前后相接的PR。父PR被squash后，将子分支自己的增量移到真实新main并重查差异，不能重复带入父分支旧提交。独立任务的实现、检查和滚动反向核验继续并行；最终合并窗口按依赖顺序协调，实际执行者按上述约定。

尽早用草稿PR展示范围和依赖。Lean代码、库入口、实际目标登记、scope状态及必要陈述记录随同一交付进入候选版本；中央文件由协调者整合，不能留待后来的总整理PR才让检查器看见新目标。新增支持代码不必把所有辅助引理都注册为论文目标；须说明其被哪个受审目标消费，独立计算按原工作流核查。纯文档或工程PR按实际影响检查；不影响数学语义者无需无关的反向核验，改变检查能力、范围或数学说明者仍审查相应影响。

## 合并前检查

1. PR说明原文位置、实际声明和重要定义、假设或条件接口、消费者及未完成项。若改变原文数学含义或补加条件，先取得该处所需用户决定，其余独立工作继续。
2. 未参与该项正向实现的代理对冻结源码独立回读；新增工程规则由未参与修改的代理审查其行为和权限边界。复核记录保留输入身份、发现及处理情况。旧复核可按实际差异复用，只补查受影响声明和依赖。
3. GitHub的`project-check`检查完整工程、切片结构、当前登记目标及其来源和传递公理。PR运行默认检出合并候选，不能改成只测head后声称组合已通过。协调者同时核对新增目标登记，绿色状态本身不判断论文语义或完整覆盖。
4. 记录PR head、目标main和候选提交、关键输入及CI运行。合并前重新读取当前main与PR head；main前进时刷新组合检查，若影响语义则补相关复核。代理已获授权通过API合并时传入受审head SHA；人类合并时，交接明确的受审head与对应CI，版本变化后先更新受影响证据，不以旧绿色状态代替当前检查。
5. CI、检查器、目标清单或保护配置的改动交独立代理审查实际差异，确认应执行的检查真实完成。同名job即使由GitHub Actions提供，也可能被改成空跑；本项目不声称平台已防住这种修改。数学清单调整不能无依据删除仍需完成的结果。

## 双语交付

同一 PR 更新受影响的中英文人读文档和 PR 说明。两版核对同一原文、实际 Lean 声明、数学范围、假设、复核及机器检查状态。沿用单份源码、机器清单与原始证据。英文译文以相邻 `.en.md` 保存，根 README 以英文为入口。

## 平台保护与协调职责

本项目约定的main保护包括：必须经PR；`project-check`由实际GitHub Actions app提供且要求分支与目标同步；管理员也受规则约束；禁止强推和删除；线性历史；代码讨论须解决。核查时逐项比较实际回读与项目约定，字段缺失或未知记证据不足；只核过管理员适用与strict不能报告整套保护通过。历史[配置回读](github-settings.json)不替代当前核查。仓库采用squash合并，不启用自动合并；分支收尾另按已有授权处理，不因合并完成自动增加删除权限。

所有代理目前共用Oho1e账号，因此GitHub要求的独立账号批准数为0，不启用“最后推送须另一人批准”。这保留PR要求，但不会让子代理报告变成GitHub Approve。若同一账号也由用户操作，“人类执行最后合并”是协作约定与工具行为边界，不能声称服务器仅凭该账号就能识别操作者。协调者须核对独立报告并解决影响正确性的异议；该条件和数学对应由流程落实。以后有真实独立协作者时，可根据参与方式调整批准要求，不自动给其他账号权限。

这不是GitHub的自动merge queue功能。协调者按依赖顺序逐个准备就绪候选，避免多个代理抢合；实际执行者依项目选择及本轮授权操作。一次性工具明确本次仓库、PR、branch及受审版本，旧脚本只保留其历史用途。`scripts/pr_readiness.py`只作无网络就绪/保护判定，不执行合并，也不代替真实API回读或独立数学复核。涉及新数学选择或超出既有远程授权时再交用户决定，不把每次PR交接变成重确认全部数学或重复申请已获授权的操作。

实际执行器采集的命令、退出码、日志及输入版本，与代理转述的历史分别标识。报告区分真实接受路径、代码检查、离线故障样本及未测路径；离线判定测试不是一次实际GitHub拒绝。相关维护样本在工具逻辑改变后按影响运行，不要求每篇论文重复整套负例或固定监督代理人数。

## 合并后

尚未合并时报告“就绪，待最终执行者合并”，不能报告本次整合完成。实际合并后，在当前会话可观察或后续获授权续接时，将PR、已复核head及实际squash提交建立对应，确认该main提交的push CI成功，再报告整合完成并更新本地main。不开启自动后台监控来等待人类点击；后续任务可从现有PR与运行记录续接。旧证据仍只证明它绑定的历史快照；新提交的机器证据由实际运行提供，不在提交内写包含它自身的SHA。

若main CI失败或结果不明，暂停后续合并、定位问题，并在修复分支上通过PR处理；不临时关闭保护或强推main来恢复绿色。main编译成功仍不消除条件接口、信任待决或作者确认待决。整篇标签只在数学标准的全部完成条件满足后使用。
