# GitHub分支、PR与合并

2026-11-15用户选择将本工程公开。本流程用于开发成果进入`main`；数学标准仍是paper-results1.2，skill与工程工作流版本为1.3。进入主分支不签发整篇形式化标签，未决信任政策和作者确认保持原状态。

## 并行工作与PR范围

从当前main按可消费的数学交付建立短期功能分支，例如一组相关的零锥引理；不按代理人数或46个切片机械建分支。不同Git检出任务使用独立worktree；共用检出目录时保持同一分支、明确文件写入责任，由协调者暂存和提交，代理不各自切换分支。

实际共享的定义先统一最小接口，消费者可基于冻结版本并行实现。只在确有依赖时使用前后相接的PR。父PR被squash后，将子分支自己的增量移到真实新main并重查差异，不能重复带入父分支旧提交。独立任务的实现、检查和滚动反向核验继续并行，最终合并窗口由协调者串行处理。

尽早用草稿PR展示范围和依赖。Lean代码、库入口、实际目标登记、scope状态及必要陈述记录随同一交付进入候选版本；中央文件由协调者整合，不能留待后来的总整理PR才让检查器看见新目标。新增支持代码不必把所有辅助引理都注册为论文目标；须说明其被哪个受审目标消费，独立计算按原工作流核查。纯文档或工程PR按实际影响检查；不影响数学语义者无需无关的反向核验，改变检查能力、范围或数学说明者仍审查相应影响。

## 合并前检查

1. PR说明原文位置、实际声明和重要定义、假设或条件接口、消费者及未完成项。若改变原文数学含义或补加条件，先取得该处所需用户决定，其余独立工作继续。
2. 未参与该项正向实现的代理对冻结源码独立回读；新增工程规则由未参与修改的代理审查其行为和权限边界。复核记录保留输入身份、发现及处理情况。旧复核可按实际差异复用，只补查受影响声明和依赖。
3. GitHub的`project-check`检查完整工程、切片结构、当前登记目标及其来源和传递公理。PR运行默认检出合并候选，不能改成只测head后声称组合已通过。协调者同时核对新增目标登记，绿色状态本身不判断论文语义或完整覆盖。
4. 记录PR head、目标main和候选提交、关键输入及CI运行。合并前重新读取当前main与PR head；main前进时刷新组合检查，若影响语义则补相关复核。合并请求传入已检查head SHA，拒绝把后来推送的未审版本一起合入。版本或结果不明时先补核对，不以旧绿色状态代替当前检查。
5. CI、检查器、目标清单或保护配置的改动交独立代理审查实际差异，确认应执行的检查真实完成。同名job即使由GitHub Actions提供，也可能被改成空跑；本项目不声称平台已防住这种修改。数学清单调整不能无依据删除仍需完成的结果。

## 平台保护与协调职责

本项目main配置：必须经PR；`project-check`由实际GitHub Actions app提供且要求分支与目标同步；管理员也受规则约束；禁止强推和删除；线性历史；代码讨论须解决。仓库采用squash合并，不启用自动合并；分支在合并后main检查成功再收尾。

所有代理目前共用Oho1e账号，因此GitHub要求的独立账号批准数为0，不启用“最后推送须另一人批准”。这保留PR要求，但不会让子代理报告变成GitHub Approve。协调者须核对独立报告并解决影响正确性的异议；该条件和数学对应由流程落实，不能把它们说成服务器已经机器强制。以后有真实独立协作者时，可根据参与方式调整批准要求，不自动给其他账号权限。

这不是GitHub的自动merge queue功能。协调者按依赖顺序逐个合并，在每次操作前重读最新候选。对于通常的开发交付，在本工程已有授权内执行；涉及新数学选择或超出既有远程授权时再交用户决定。不把每次PR合并变成重新确认全部数学或重复申请发布权限。

## 合并后

将PR、已复核head及实际squash提交建立对应，确认该main提交的push CI成功，然后更新本地main并从新main开始后续分支。旧证据仍只证明它绑定的历史快照；新提交的机器证据由实际运行提供，不在提交内写包含它自身的SHA。

若main CI失败或结果不明，暂停后续合并、定位问题，并在修复分支上通过PR处理；不临时关闭保护或强推main来恢复绿色。main编译成功仍不消除条件接口、信任待决或作者确认待决。整篇标签只在数学标准的全部完成条件满足后使用。
